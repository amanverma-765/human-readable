# Human-Readable Prose for Coding Agents

## Overview

Text generated by modern frontier AI models frequently exhibits severe psycholinguistic compression—informally called **"Claudish"** or "AI dialect". As proven by Clark, Martin, and Mahowald (2026), post-training models for code and math under length penalties creates an unnatural preference for hyper-compressed, non-human syntax that overloads human working memory and triggers mental parsing reanalysis.

This skill equips coding agents with the syntactic rules and a deterministic verification tool (`readable`) to ensure that all written communication—whether explanations, architectural reviews, PR descriptions, or documentation—is effortless for human engineers to comprehend.

---

## When to Use

Activate this skill when:
- Writing responses, explanations, or summaries intended for human readers.
- Drafting or modifying pull request descriptions, commit messages, or code reviews.
- Writing technical documentation, ADRs, or guides in Markdown.
- Reviewing agent-generated text for cognitive readability before presenting it to the user.

## Core Syntactic Standards (The Six Cognitive Rules)

Always prioritize **human ease of comprehension** over token brevity. Human natural language evolved under Uniform Information Density (UID): optional words exist to prevent cognitive channel overload.

### 1. Explicit Function Words (Retain Optional "That")
* **Rule:** Never strip optional relativizers (*that*, *which*, *who*) or complementizers.
* **Why:** Dropping *"that"* saves 1 token but triggers temporary garden-path ambiguity and structural reanalysis in human working memory.
* **Target:**
  - Write: *"The bug that the team identified..."* (not: *"The bug the team identified..."*)
  - Write: *"The engineer was sure that the branch was merged."* (not: *"The engineer was sure the branch was merged."*)
  - Write: *"We optimized the query so that the page loads quickly."* (not: *"We optimized the query so the page loads quickly."*)

### 2. Unpack Compound Noun Chains (No 3+ Stacked Nouns)
* **Rule:** Limit noun modifiers to at most two words. When 3 or more nouns appear in succession, unpack them using prepositional phrases.
* **Why:** Sequences of 3+ nouns force the reader's brain to make complex hierarchical bracketing decisions (e.g. $[A [B\ C]]$ vs $[[A\ B] C]$), causing measurable eye-fixation regressions.
* **Target:**
  - Write: *"budget for reader patience"* (not: *"reader-patience budget"*)
  - Write: *"funds from the brokerage money market"* (not: *"brokerage money market funds"*)
  - Write: *"requirement to shut down during class time"* (not: *"class-time shutdown requirement"*)
  - Write: *"prevention of dry-run writes"* (not: *"dry-run write prevention"*)

### 3. Selectional Restriction & Agency Alignment (No Inanimate "Eaters")
* **Rule:** Never assign verbs requiring human agency, volition, physical consumption, or psychological consciousness to inanimate code or abstract entities.
* **Why:** Inanimate subjects with animate action verbs trigger a measurable P600 ERP brainwave in human readers, signaling cognitive repair and confusion.
* **Target:**
  - Write: *"The developer omitted bytes in the check"* (not: *"The check forgot bytes"*)
  - Write: *"The exception handler intercepts errors"* (not: *"The script swallows errors"*)
  - Write: *"The docstring specifies that files are skipped"* (not: *"The docstring promises..."*)
  - Write: *"This condition causes an unexpected state"* (not: *"The check bites"* or *"chaos expects you to..."*)

### 4. Use Established Verbs (No Ad-Hoc Denominal Coercions)
* **Rule:** Do not convert prototypical nouns into verbs on the fly.
* **Why:** Part-of-speech conversion forces category re-parsing, slowing down reading fluency.
* **Target:**
  - Write: *"Add a footnote to the explanation"* (not: *"Footnote it"*)
  - Write: *"Schedule it on the calendar"* (not: *"Calendar it"*)
  - Write: *"Create a hidden dot-directory"* (not: *"Dotfolder it"*)
  - Write: *"Suitable for high-speed playback"* (not: *"Speed-runnable"*)
  - Write: *"Take action on this ticket"* (not: *"Action this"*)

### 5. Dependency Proximity & Sentence Breathing Room
* **Rule:** Keep subjects and verbs close together. Avoid sentences exceeding 30 words without punctuation breaks. Break long sentences at logical clause boundaries.
* **Why:** Under Dependency Locality Theory (DLT), human working memory decays rapidly over distance. Long intervening clauses deplete memory and degrade retention.
* **Target:**
  - Write: *"The guitar sitting in the corner teaches you zero chords if you remain indecisive."*
  - (not: *"The guitar sitting in the corner because you're still 'deciding' teaches you zero chords."*)

### 6. Plain Phrasing Over AI Mannerisms
* **Rule:** Cut empty AI mannerisms and high-surprisal low-frequency clichés. Speak plainly and directly.
* **Target:**
  - Avoid: *"delve into"*, *"rich tapestry"*, *"serves as a testament to"*, *"verified red"*, *"quietly eating its own"*, *"it is worth noting that"*.
  - Write: State the finding or action directly without rhetorical throat-clearing.

## Deterministic Verification Workflow

Before returning any substantial text or committing markdown files, run the deterministic `readable` tool.

### 1. Verify Inline Text or Output
```bash
python3 -m readable -s "Your proposed text here."
```

### 2. Verify Markdown Files or PR Summaries
```bash
python3 -m readable path/to/document.md
```

### 3. Check for Strict Compliance
In strict mode, any violation (error or warning) exits with code 1:
```bash
python3 -m readable --strict path/to/document.md
```

### 4. Automated CI / Pre-Commit Check
```bash
# Verify all markdown documentation in the project
python3 -m readable --strict docs/*.md
```

---

## Completion Criteria

The human-readable standard is satisfied when:
1. Every rule check passes with **0 errors and 0 warnings** under `python3 -m readable --strict`.
2. All technical sentences state agency directly, unpack dense modifier chains, and include explicit function words (*that*).
